Internal Event Schema Contract

This document defines the schema contracts for all Redis pub/sub messages and job queue events used internally by the pixel-pet-arena backend (apps/api). These contracts govern communication between the API request handlers, background workers, and any future microservices. Consumers must validate incoming payloads against the schemas defined here and reject or dead-letter events that fail validation rather than silently processing corrupt data.

Job Queue Architecture

All background jobs use a Redis-backed queue (BullMQ) with the queue name prefixed ppa:jobs:. Each job payload is a JSON object stored as a BullMQ job data field. Workers run within the same apps/api process in the current architecture but are designed to be extractable into standalone workers without payload schema changes. Job IDs are UUIDs generated by the enqueuing code; BullMQ's internal numeric IDs are not exposed in business logic.

Three primary job queues exist: ppa:jobs:pet-generation, ppa:jobs:arena-battle, and ppa:jobs:gdpr-erasure. Each queue has a single dedicated worker handler registered at startup. Cross-queue dependencies are handled by having one job enqueue another upon completion—workers never call other workers directly. All job data fields are serialised as JSON; no binary payloads are used.

Pet Generation Job

Queue: ppa:jobs:pet-generation

Enqueued by: POST /api/v1/pet/generate request handler.

Consumed by: PetGenerationWorker.

Payload Schema

{
  "jobType": "PET_GENERATION",
  "jobId": "uuid-v4",
  "playerId": "uuid-v4",
  "requestedAt": "ISO-8601 datetime string",
  "generationSeed": "hex string (32 chars)",
  "allowedSpeciesPool": ["glacicat", "pyrofox", "stoneback", "zephyrwing"]
}
FieldTypeRequiredDescription
jobTypestringYesMust be "PET_GENERATION" — used for worker routing validation
jobIdstring (UUID)YesStable ID used for idempotency checks
playerIdstring (UUID)YesThe player who triggered generation
requestedAtstring (ISO-8601)YesWall-clock time at enqueue; used for SLA monitoring
generationSeedstringYes32-char hex seed for deterministic sprite and stat generation
allowedSpeciesPoolstring[]YesNon-empty array; controls which species the RNG selects from

Worker Output Contract

On success the worker writes the new pet record to PostgreSQL/Supabase and publishes a PET_GENERATED Redis pub/sub event (see Redis Pub/Sub Events section). On failure after all retries are exhausted, the worker publishes a PET_GENERATION_FAILED event and marks the player's pending generation slot as failed in the database so the player frontend can display an error and allow a retry.

Arena Battle Job

Queue: ppa:jobs:arena-battle

Enqueued by: POST /api/v1/arena/battle request handler (after validating the challenge and move selection).

Consumed by: ArenaBattleWorker.

Payload Schema

{
  "jobType": "ARENA_BATTLE",
  "jobId": "uuid-v4",
  "battleId": "uuid-v4",
  "challengeId": "uuid-v4",
  "playerPetId": "uuid-v4",
  "opponentPetId": "uuid-v4",
  "playerMoveId": "ice_shard",
  "enqueuedAt": "ISO-8601 datetime string",
  "battleEngineVersion": "1"
}
FieldTypeRequiredDescription
jobTypestringYesMust be "ARENA_BATTLE"
jobIdstring (UUID)YesIdempotency key
battleIdstring (UUID)YesPre-allocated battle record ID
challengeIdstring (UUID)YesThe challenge this battle resolves
playerPetIdstring (UUID)YesAttacking player's pet
opponentPetIdstring (UUID)YesOpponent pet drawn from matchmaking
playerMoveIdstringYesMove slug selected by the player (e.g. "ice_shard")
enqueuedAtstring (ISO-8601)YesEnqueue timestamp for latency SLA tracking
battleEngineVersionstringYesEngine version string; workers must reject jobs for unsupported versions

Worker Output Contract

The battle worker computes the full turn-by-turn simulation, persists the result to the battles table in PostgreSQL, updates both pets' experience and level in a single transaction, and publishes a BATTLE_RESOLVED Redis pub/sub event. The POST /api/v1/arena/battle endpoint currently runs the battle synchronously in-process for sub-200ms battles; the job queue path exists for battles projected to take longer and for future async WebSocket delivery.

GDPR Erasure Job

Queue: ppa:jobs:gdpr-erasure

Enqueued by: DELETE /api/v1/admin/users/:id/gdpr-erase request handler (superadmin only).

Consumed by: GdprErasureWorker.

Payload Schema

{
  "jobType": "GDPR_ERASURE",
  "jobId": "uuid-v4",
  "playerId": "uuid-v4",
  "requestedByAdminId": "uuid-v4",
  "requestedAt": "ISO-8601 datetime string",
  "erasureScope": ["account", "pets", "battle_history", "leaderboard_entries"],
  "auditToken": "hex string (64 chars)"
}
FieldTypeRequiredDescription
jobTypestringYesMust be "GDPR_ERASURE"
jobIdstring (UUID)YesIdempotency key; duplicate jobs with same jobId are skipped
playerIdstring (UUID)YesPlayer to erase
requestedByAdminIdstring (UUID)YesAudit trail: which admin issued the request
requestedAtstring (ISO-8601)YesTimestamp for regulatory audit log
erasureScopestring[]YesMust be the full set ["account","pets","battle_history","leaderboard_entries"]; partial erasure is not supported
auditTokenstringYes64-char hex token stored in the immutable audit log before erasure begins

Worker Output Contract

The worker performs erasure steps in order: revoke player bearer token → anonymise battle history records (replace display name with [deleted]) → delete pet records → delete player account row. Each step is wrapped in a database transaction. After all steps succeed the worker writes a completion record to the gdpr_erasure_log table (which is retained for regulatory purposes despite the player data being removed) and publishes a GDPR_ERASURE_COMPLETE Redis pub/sub event. This job has no retry budget beyond 1 attempt because partial erasure on retry could leave inconsistent state; failures are escalated to the ppa:jobs:gdpr-erasure:dead dead-letter queue and alert the on-call engineer.

Redis Pub/Sub Event Schemas

Beyond job queues, the API publishes real-time notification events on Redis pub/sub channels for internal fan-out.

PET_GENERATED

Channel: ppa:events:pet

{
  "eventType": "PET_GENERATED",
  "petId": "uuid-v4",
  "playerId": "uuid-v4",
  "species": "glacicat",
  "spriteKey": "glacicat_blue_lv1",
  "publishedAt": "ISO-8601 datetime string"
}

Consumed by: WebSocket notification handler (to push pet-ready notification to the player frontend).

BATTLE_RESOLVED

Channel: ppa:events:battle

{
  "eventType": "BATTLE_RESOLVED",
  "battleId": "uuid-v4",
  "outcome": "win",
  "playerPetId": "uuid-v4",
  "opponentPetId": "uuid-v4",
  "publishedAt": "ISO-8601 datetime string"
}

Consumed by: leaderboard cache invalidation handler; WebSocket notification handler.

GDPR_ERASURE_COMPLETE

Channel: ppa:events:admin

{
  "eventType": "GDPR_ERASURE_COMPLETE",
  "playerId": "uuid-v4",
  "erasedAt": "ISO-8601 datetime string",
  "requestedByAdminId": "uuid-v4"
}

Consumed by: Redis session cleanup handler (invalidates any active admin or player sessions for the erased player ID).

Error and Retry Policy

Job queue retry behaviour is configured per queue in BullMQ options:

QueueMax AttemptsBackoff StrategyBackoff Delay
ppa:jobs:pet-generation3Exponential2 s base
ppa:jobs:arena-battle3Exponential1 s base
ppa:jobs:gdpr-erasure1NoneN/A

Failed jobs that exhaust all retry attempts are moved to the corresponding dead-letter queue (<queue-name>:dead). A monitoring process polls dead-letter queues every 60 seconds and emits a structured log entry at error level; a Supabase-backed alert rule fires a PagerDuty notification when dead-letter depth exceeds 5 entries. Workers must never throw unhandled errors—all exceptions must be caught, logged with the jobId and jobType, and re-thrown so BullMQ can manage the retry/fail lifecycle correctly. Idempotency is enforced for all three job types: before executing, each worker checks whether a success record already exists for the given jobId and returns early if so, preventing duplicate side effects on BullMQ at-least-once delivery.
